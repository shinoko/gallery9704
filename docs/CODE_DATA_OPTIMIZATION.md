# 代码与数据优化方案

本文记录 GALLERY9704 的代码结构、数据存储和维护流程优化建议，作为后续重构依据。本文仅描述方案，不代表相关改造已经实施。

审查日期：2026-08-05。

## 当前基线

- 技术结构：原生 HTML、CSS、JavaScript，加 Node.js 本地服务。
- 前端主逻辑 `js/main.js` 约 1,400 行。
- 站姐数据 1,181 条，官方数据 553 条，共 1,734 条。
- 数据中共包含 8,644 个图片路径引用。
- `js/data.js` 和 `js/official-data.js` 合计约 2 MB，页面启动时会同时加载。
- 两份源数据没有发现重复 `postUrl`，现有日期字段格式正常。
- 共有 20 条记录的 `rawPicNum` 与 `imageFiles.length` 不一致。
- 站姐数据中有 1,024 条记录没有显式 `id`，目前主要依赖 `postUrl` 标识。

## 优化项目

### P0：数据写入可靠性

当前维护接口会直接覆盖元数据 JSON，然后重新生成前端数据文件。如果写入、构建或多个页面同时保存时发生异常，源数据和生成数据可能不同步。

建议：

1. 先将新数据写入同目录临时文件。
2. 完成 JSON 解析、Schema 校验和静态数据构建预检。
3. 所有步骤成功后，通过原子重命名替换正式文件。
4. 服务端为同一数据集建立串行写入队列，避免多页面并发覆盖。
5. 写入前生成可恢复备份，并限制备份保留数量。

涉及位置：`server.js` 的 `writeMetadata`、`updateRecord` 和 `deleteRecords`。

### P0：统一数据校验

目前导入、清洗、维护保存和静态构建缺少统一的数据结构校验。部分未知平台值还会被静默归类为微博。

建议定义一份 JSON Schema，至少校验：

- 永久且唯一的记录 ID；
- `platform` 只能为允许值；
- `postUrl`、`postDate`、`shootDate` 的格式；
- `tags`、`targetPeople`、`imageFiles` 必须为字符串数组；
- 图片路径必须为项目内相对路径；
- 图片数量字段与 `imageFiles.length` 一致；
- 同一数据集内 `postUrl`、平台原始 ID 不得重复。

所有写入入口应复用同一个验证模块，并提供独立的只读审计命令，例如 `npm run audit:data`。

### P1：建立单一规范数据模型

源数据和浏览数据目前使用不同字段，例如：

| 源数据字段 | 浏览数据字段 |
| --- | --- |
| `shootDate` | `date` |
| `imageFiles` | `images` |
| `maintenanceNote` | `note` |
| `targetPeople` | `people` |

建议前后端统一使用源数据字段名。只在界面展示层格式化文案，不再创建第二套语义相同的字段。

推荐的记录结构可以分为：

- 核心字段：`id`、`platform`、`postUrl`、`author`、`postDate`、`shootDate`、`theme`、`text`、`tags`、`imageFiles`；
- 来源信息：放入 `source` 对象，例如原始平台 ID、采集账号、采集时间；
- 维护信息：放入 `maintenance` 对象，例如状态、备注和最后更新时间。

`rawPicNum`、`imageCount`、`xhsImageCount` 等可计算字段应尽量不持久化；需要展示时统一由 `imageFiles.length` 计算。

### P1：减少重复数据和启动加载量

当前同时保存源 JSON 和生成 JS，且页面启动时无论选择哪个数据集，都会加载两份生成数据。

建议分两步处理：

1. 将生成文件改为精简 JSON，通过 `fetch` 按数据集加载；初始只加载默认数据集。
2. 数据继续增长后，按照数据集和年份拆分清单，例如 `data/station/2025.json`。

浏览器只加载当前需要的分片；筛选跨年份时再按需加载。静态部署应开启 gzip 或 Brotli 压缩及长期缓存。

当前规模仍适合继续使用 JSON。只有出现多人同时维护、复杂关联查询或大量修改历史时，才考虑迁移到 SQLite。

### P1：集中管理主题和业务枚举

活动主题、日期和匹配规则目前同时存在于前端主题时间线和清洗脚本中，容易产生漂移。

建议增加统一配置文件，例如：

```text
config/themes.json
config/accounts.json
config/platforms.json
```

主题配置应同时包含标准名称、日期或日期范围、排序顺序、关键词别名。前端筛选、维护选项和清洗脚本都从同一配置生成。

账号显示别名等业务规则也不应硬编码在界面函数中。

### P1：拆分前端主文件

建议将 `js/main.js` 按职责拆分为 ES Modules：

```text
js/
├── app.js
├── state.js
├── data-service.js
├── filters.js
├── date-picker.js
├── gallery.js
├── modal.js
└── maintenance.js
```

模块之间通过明确的状态和事件接口协作，避免直接读取或修改大量全局变量。

可以同时改进：

- 使用事件委托代替为每张卡片和图片创建独立监听器；
- 预先生成规范化搜索文本，避免每次筛选重复拼接和小写转换；
- 将通用日期、平台和 ID 处理提取为纯函数；
- 避免使用字符串模板拼接数据属性，改用 DOM API、`textContent` 和 `setAttribute`。

### P1：建立自动化测试

项目目前没有测试命令。可以优先使用 Node 内置的 `node:test`，不必立即引入大型测试框架。

首批测试范围：

- 源数据到浏览数据的转换；
- 日期解析和主题识别；
- 平台、账号和标签规范化；
- 重复记录检测；
- 图片引用计数；
- 原子保存失败时不破坏正式数据；
- 删除记录时不删除仍被引用的图片；
- 筛选边界和排序规则。

建议增加以下命令：

```text
npm test
npm run audit:data
npm run build:data:check
```

其中 `build:data:check` 只验证生成文件是否与源数据一致，不写入文件。

### P2：稳定 ID

所有记录应拥有永久 ID，不能使用数组位置作为兜底值。

建议：

- 微博优先使用平台固定 ID，并加平台前缀；
- 小红书使用 `noteId`，并加平台前缀；
- 对无法获得平台 ID 的旧记录生成一次性 UUID，并写回源数据；
- `postUrl` 作为可变业务字段，不作为数据库式主键的唯一来源。

### P2：改进采集与导入事务

导入流程目前可能先复制图片、再写 JSON，并在完成后直接删除采集目录中的中间图片。

建议采用三个阶段：

1. 预检：生成新增、重复、冲突、缺图和字段异常报告，不修改正式数据。
2. 提交：复制到临时目录，验证后原子合并数据和图片。
3. 清理：提交成功并完成审计后，再清理采集目录。

采集输入目录应通过命令参数显式提供，不应长期保留带时间戳的默认路径。

## 推荐实施顺序

1. 增加 Schema、只读数据审计和稳定 ID。
2. 实现原子写入、备份和服务端写入队列。
3. 合并主题配置与业务枚举。
4. 统一源数据和浏览数据字段模型。
5. 改为数据集按需加载，并在需要时按年份分片。
6. 拆分 `main.js`，为纯函数和维护接口补充测试。

每个阶段都应保持当前静态导出能力，并在迁移完成前兼容旧数据格式。
